# Marine Service — Django + DRF Refactor Design

**Date:** 2026-04-05
**Branch:** week6-ayos
**Author:** Brainstormed with Claude Code

## Overview

Refactor the MERMAID marine service from FastAPI to Django + Django REST Framework (DRF). The service gains a PostgreSQL database for zone definitions and configurable risk thresholds. All existing API contracts (URLs, response shapes, auth header) remain unchanged so the Java backend requires no modifications.

---

## Goals

- Replace FastAPI with Django + DRF as the web framework
- Add PostgreSQL database (reusing `mermaid_db`) for:
  - `FishingZone` — replace hardcoded `ZONES` dict with DB-managed records
  - `RiskThreshold` — replace hardcoded scoring tables with DB-managed rows
  - `RiskConfig` — global risk level cutoffs, admin-editable
- Keep in-memory TTL cache (15 min conditions, 1 hr forecast) — aligned to Open-Meteo's 15-min update cadence
- Keep all 5 API endpoints at identical URLs with identical response shapes
- Sync views with `ThreadPoolExecutor` for parallel zone fetching (replaces `asyncio.gather`)

## Non-Goals

- No Redis or persistent cache (in-memory TTL is sufficient for single-process dev)
- No historical conditions log
- No API key DB table (single static key from `.env` is sufficient for now)
- No gunicorn (added later during Docker/production setup)

Replaces the hardcoded `ZONES` dict in `conditions.py`. Seeded via data migration.

| Field | Type | Notes |
|-------|------|-------|
| `id` | `CharField(primary_key=True)` | e.g. `"sto_tomas"` |

| `lat` | `FloatField` | |

### `RiskThreshold`

One row per scoring tier per parameter. Replaces `_WAVE_SCORES` and `_WIND_SCORES` in `risk_engine.py`. The sentinel "infinity" tier uses `upper_bound=9999.0` — this is a safe approximation since wave heights max at ~20 m and wind speeds well under 500 km/h in real-world conditions.

| Field | Type | Notes |
|-------|------|-------|
| `id` | `AutoField` | |
| `parameter` | `CharField(choices)` | `WAVE`, `WIND` |
| `upper_bound` | `FloatField` | use `9999.0` for the final "infinity" tier |
| `score_points` | `IntegerField` | points added when value ≤ upper_bound |
| `order` | `IntegerField` | evaluation order (ascending); rows sorted by this before use |

**Default rows seeded in `0002_seed_data.py` (exact values from `risk_engine.py`):**

WAVE tiers (parameter=`WAVE`, in order):

| order | upper_bound | score_points |
|-------|-------------|--------------|
| 1 | 1.25 | 0 |
| 2 | 2.50 | 3 |
| 3 | 4.00 | 6 |
| 4 | 9999.0 | 9 |

WIND tiers (parameter=`WIND`, in order):

| order | upper_bound | score_points |
|-------|-------------|--------------|
| 1 | 30.0 | 0 |
| 2 | 60.0 | 2 |
| 3 | 100.0 | 5 |
| 4 | 9999.0 | 8 |

## API Endpoints

All URLs unchanged. Java backend requires no modifications.

| Method | URL | Auth | View |
|--------|-----|------|------|
| `GET` | `/api/health` | None | `HealthView` |
| `GET` | `/api/conditions/zones` | None | `ZoneListView` |
| `GET` | `/api/conditions` | `X-API-Key` | `AllConditionsView` |
| `GET` | `/api/conditions/<str:zone_id>/forecast` | `X-API-Key` | `ZoneForecastView` |
| `GET` | `/api/conditions/<str:zone_id>` | `X-API-Key` | `ZoneConditionsView` |

**URL ordering is critical:** In `conditions/urls.py`, the `forecast` path must be registered before the `<str:zone_id>` path so Django does not match `sto_tomas/forecast` as a zone ID:

```python
urlpatterns = [
    path("zones", ZoneListView.as_view()),
    path("<str:zone_id>/forecast", ZoneForecastView.as_view()),  # MUST be before zone_id
    path("<str:zone_id>", ZoneConditionsView.as_view()),
    path("", AllConditionsView.as_view()),
]
```

### Authentication

API-key auth uses a two-part DRF pattern:

**`ApiKeyAuthentication`** (in `conditions/authentication.py`) — a `BaseAuthentication` subclass. `authenticate()` reads `X-API-Key` from the request headers. If present and matches `settings.MARINE_API_KEY` (compared with `hmac.compare_digest` for timing safety), returns `(None, key)`. If missing, returns `None` (defers to next authenticator). If present but wrong, raises `AuthenticationFailed`.

**`HasValidApiKey`** (in `conditions/authentication.py`) — a `BasePermission` subclass. `has_permission()` returns `True` if `request.auth` is not `None` (i.e., the key was validated). This replaces `IsAuthenticated`, which requires a Django `User` object. Protected views use:

```python
authentication_classes = [ApiKeyAuthentication]
permission_classes = [HasValidApiKey]
```

Public views (`HealthView`, `ZoneListView`) set `authentication_classes = []` and `permission_classes = []`.

### `HealthView` Response

Matches the existing `HealthResponse` Pydantic model exactly (the Java backend or monitoring may rely on this shape):

```json
{
  "status": "ok",
  "version": "1.0.0",
  "timestamp": "2026-04-05T10:00:00Z",
  "cache_entries": 12
}
```

`cache_entries` is read from the same `TTLCache` instance as before.

### `ZoneListView` and `ZoneConditionsView` / `ZoneForecastView` Behaviour

**`ZoneListView`** queries `FishingZone.objects.filter(is_active=True)` only — consistent with the soft-delete pattern used throughout the monorepo. Inactive zones are never returned.

**`ZoneConditionsView` and `ZoneForecastView`** look up zones with a manual query + explicit `NotFound` to preserve the custom error message from the existing API contract:

```python
zone = FishingZone.objects.filter(pk=zone_id, is_active=True).first()
if zone is None:
    raise NotFound(
        detail=f"Zone not found: '{zone_id}'. Call GET /api/conditions/zones for valid IDs."
    )
```

Do **not** use `get_object_or_404` — it raises `Http404` with a generic message before the custom `NotFound` message can be set.

### Parallel Fetching (`AllConditionsView`)

Uses `concurrent.futures.ThreadPoolExecutor`. Per-zone exceptions are caught individually to match the existing graceful-degradation behaviour (failed zones are logged and skipped, not propagated).

`AllConditionsView` also replicates the current caching side-effect: each successfully fetched zone result is written to the per-zone cache key (`conditions:{zone_id}`), and the aggregate result is written to `conditions:all`. This means a call to `/api/conditions` warms the cache for all subsequent `/api/conditions/{zone_id}` calls, matching the existing FastAPI behaviour.

```python
# Check aggregate cache first — return early if warm
cached_all = cache.get("conditions:all")
if cached_all:
    return Response(AllConditionsSerializer(cached_all, many=True).data)

def _fetch_zone_safe(zone, client, cache):
    cache_key = f"conditions:{zone.id}"
    cached = cache.get(cache_key)
    if cached:
        return cached
    try:
        result = open_meteo.fetch_current_conditions(zone, client)
        cache.set(cache_key, result, settings.CONDITIONS_CACHE_TTL)
        return result
    except Exception as exc:
        logger.warning("Failed to fetch zone %s: %s", zone.id, exc)
        return None

zones = list(FishingZone.objects.filter(is_active=True))
with ThreadPoolExecutor(max_workers=len(zones)) as executor:
    futures = [executor.submit(_fetch_zone_safe, zone, client, cache) for zone in zones]
    results = [f.result() for f in futures]

zones_data = [r for r in results if r is not None]
# write aggregate cache key
cache.set("conditions:all", zones_data, settings.CONDITIONS_CACHE_TTL)
```

### Open-Meteo Error Handling in Views

The existing `_open_meteo_errors` async context manager is replaced with a try/except block in each view's `get()` method:

```python
try:
    conditions = open_meteo.fetch_current_conditions(zone, client)
except (httpx.HTTPStatusError, httpx.RequestError) as exc:
    logger.error("Open-Meteo error for %s: %s", zone_id, exc)
    raise ValidationError({"detail": "Marine data service temporarily unavailable"})
    # or: return Response({...}, status=503)
```

Single-zone views (`ZoneConditionsView`, `ZoneForecastView`) return HTTP 503 on upstream failure. `AllConditionsView` silently skips failed zones and returns 503 only if all zones fail.

## Services Layer

### `services/open_meteo.py`

Rewritten as synchronous. Changes:
- `httpx.AsyncClient` → `httpx.Client` (synchronous)
- All `async def` → `def`, all `await` removed
- The inner `asyncio.gather(marine_req, weather_req)` in `_fetch_both` replaced with `ThreadPoolExecutor(max_workers=2)` to keep the marine+weather concurrent fetch per zone
- All parsing logic (`_parse_marine_current`, `_parse_weather_current`, `_build_hourly_points`, `_aggregate_daily`) is **unchanged**

The shared `httpx.Client` instance is created in `AppConfig.ready()` (inside `conditions/apps.py`) and stored on the `AppConfig` instance. Views retrieve it via `apps.get_app_config("conditions").http_client`. This provides proper lifecycle management — the client is created once after Django setup and is accessible without circular imports.

```python
# conditions/apps.py
import atexit
import httpx
from django.apps import AppConfig

class ConditionsConfig(AppConfig):
    name = "conditions"

    def ready(self):
        from django.conf import settings
        self.http_client = httpx.Client(
            timeout=settings.HTTP_TIMEOUT,
            headers={"Accept": "application/json", "User-Agent": "MERMAID-MarineService/1.0"},
            follow_redirects=True,
        )
        # Close connection pool on process exit (covers both normal shutdown and dev reload)
        atexit.register(self.http_client.close)
```

### `services/risk_engine.py`

`compute_risk(marine, weather)` signature unchanged.

Threshold loading uses a `threading.Lock` to avoid a race condition on the first call (Django dev server is multi-threaded):

```python
_cache = {}
_lock = threading.Lock()

def _load_thresholds():
    with _lock:
        if _cache:
            return _cache
        wave_rows = RiskThreshold.objects.filter(parameter="WAVE").order_by("order")
        wind_rows = RiskThreshold.objects.filter(parameter="WIND").order_by("order")
        config = RiskConfig.objects.first()
        if config is None:
            raise RuntimeError(
                "RiskConfig row not found. Run migrations (python manage.py migrate) "
                "to seed the default configuration."
            )
        _cache["wave"] = [(r.upper_bound, r.score_points) for r in wave_rows]
        _cache["wind"] = [(r.upper_bound, r.score_points) for r in wind_rows]
        _cache["config"] = config
        return _cache
```

`RiskConfig.objects.first()` raises `RuntimeError` if no row exists — a fast, clear failure with an actionable message. The seed migration (`0002_seed_data.py`) guarantees the row is present after `manage.py migrate`.

The reconstructed lists are in `list[tuple[float, int]]` format — identical to the current hardcoded `_WAVE_SCORES` / `_WIND_SCORES` — so `_score_from_table` is unchanged. The `9999.0` sentinel rows serve as the "catch-all" last entry, matching the `float("inf")` behaviour.

The cache is invalidated on Django startup (module reload). It is not invalidated on DB changes within a running process — an admin editing thresholds requires a server restart for changes to take effect. This is acceptable for MVP.

### Pydantic Models

The internal Pydantic models (`MarineData`, `WeatherData`, `ZoneConditions`, `HourlyForecastPoint`, etc.) in `app/models/marine.py` are **moved to `services/models.py`** and kept as Pydantic models. They are used internally by the service layer as typed data containers. DRF serializers sit at the view boundary and serialize these Pydantic objects into JSON responses. Pydantic stays in `requirements.txt` for this reason.

**`FishingZone` type boundary:** `open_meteo.fetch_current_conditions` and `open_meteo.fetch_forecast` accept the Django ORM `FishingZone` model directly via duck typing — both the Pydantic and Django ORM models expose `.id`, `.lat`, `.lng`, and `.name` with the same names. No conversion step is needed at the view boundary. The Pydantic `FishingZone` in `services/models.py` is kept only for the response shape (nested inside `ZoneConditions`) — it is instantiated inside `open_meteo.py` from the ORM instance's fields when building the response object.

Database: `mermaid_db` on `localhost:5432` — same Postgres instance used by the Java backend. Django creates `conditions_` prefixed tables and `django_` prefixed system tables, no conflicts with existing Spring/Flyway-managed tables.
